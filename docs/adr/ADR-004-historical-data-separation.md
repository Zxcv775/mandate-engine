# ADR-004 · 历史模板数据与运行状态分离

- 状态：**已接受**
- 日期：2026-07-26

## 背景

游戏既需要可信的历史初始条件（人物、官职、制度、事件、经济数据），
又需要玩家能够改变历史进程。若模板与状态混在一起，
修改会污染"史实基线"，且无法回答"哪些被玩家改变过"。
同时，所有历史数据必须可绑定史料来源并标注确认状态。

## 决策

1. **模板只读**：历史模板存于 `data/`（JSON，git 版本控制），
   经只读加载器进入内存；任何写操作抛错（FR-HIST-002）；
2. **来源强制标注**：模板数据必须携带 `meta.sourceIds`（关联 HistoricalSource）
   与 `meta.confirmation`（confirmed / disputed / inferred / gameplay-adjusted）；
3. **运行状态独立存储**：GameState 实例化自模板后与之脱钩，
   持久化于 SQLite（node:sqlite）：`saves` 存快照，`state_change_log` 存变更审计；
4. **版本迁移**：快照带 `schema_version`，加载走迁移链；
5. 网络传说、文学演义不得作为 `primary` 来源；争议信息标 disputed 而非定论。

## 选择理由

- 历史诚实：来源与确认状态一目了然；
- 可玩性：玩家改变历史不污染模板；
- 可维护：模板修正（勘误）不影响已有存档语义。

## 替代方案

- 模板与状态同库同表：混淆基线，拒绝；
- 全部 JSON 文件（无 SQLite）：日志查询与多槽位管理弱，已评估否决（见技术选型第 5 项）；
- 模板入库（SQLite 只读表）：失去 git diff 与人工编辑便利，拒绝。

## 后果

- 正面：史实基线可信、变更可审计、模板可独立迭代；
- 负面：实例化/加载层需要维护模板→运行时的映射；
- node:sqlite 为 experimental 稳定性（CONFLICT-002）：薄仓储层隔离，必要时换 better-sqlite3。

## 风险

- 模板数据质量依赖人工录入与校验 → Phase 7 配数据校验脚本与 Historian 报告；
- 存档体积随回合增长 → 快照压缩与日志归档在 Phase 9 评估。
