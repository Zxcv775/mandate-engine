# ADR-003 · 数据驱动设计：Modifier + 条件 DSL

- 状态：**已接受**
- 日期：2026-07-26

## 背景

游戏包含财政、军事、灾害、派系、人物态度等大量相互影响的规则。
若以硬编码 if-else 实现，规则将不可维护、不可测试、无法数据化调整，
也无法支持"新朝代只加数据"的扩展目标。

## 决策

1. 一切数值影响统一表达为 **Modifier**（targetPath + operation + value + 可选 condition/duration）；
2. 触发条件与生效条件以**白名单条件表达式 DSL** 表达（数据字符串），
   由自研求值器解释执行——**禁止 eval / new Function**；
3. 规则引擎负责 Modifier 的收集、排序、合成、结算与到期清理；
4. 朝代/剧本差异通过制度包与规则数据表达，核心引擎保持朝代无关。

## 选择理由

- 规则即数据：可校验（Schema）、可测试（确定性）、可平衡（改数据不改代码）；
- DSL 白名单保证安全（LLM/玩家输入不可能注入代码）；
- Modifier 天然支持叠加与溯源（StateChangeLog.ruleRefs）。

## 替代方案

- 硬编码规则：拒绝（不可维护）；
- 引入成熟表达式库（如 expr-eval、json-logic）：可用但语义需定制；
  决策为自研小型求值器，若复杂度失控可在 Phase 5 重新评估引入 json-logic；
- 脚本语言（Lua/JS 沙箱）：能力过剩且安全成本高，拒绝。

## 后果

- 正面：规则可数据化调平衡、可单测、可溯源；
- 负面：DSL 需要设计文档与测试覆盖；复杂规则的表达力有限（复杂逻辑留在引擎代码中，
  只把"参数与条件"数据化）。

## 风险

- DSL 表达力不足 → 渐进扩展语法，保持白名单；
- 求值器 bug → Phase 5 要求求值器本身 100% 分支测试覆盖。
